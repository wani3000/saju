# 무료 이용권과 유료 결제 설계

## 상품 규칙

첫 상대 한 명 무료, 이후 새 상대 비교당 2,900원. 최종 결제 표시 금액은 2,900원으로 통일하는 기획이며 세무 처리·PG 수수료는 계약 단계에서 확정한다. 다시 보기와 같은 결과 공유는 무료다. 동일한 비교를 중복 구매하지 않게 한다.

무료는 완성 결과 한 건을 받은 시점에 소비한다. 생성 실패·서버 중단 때문에 무료 기회를 잃게 하지 않는다. 단, 익명 체험은 새 브라우저/새 세션을 완전히 구별할 수 없어 ‘실제 사람 평생 딱 한 번’을 기술적으로 보장하지 못한다. 서버 계정 단위 1회 + 요청 제한을 MVP 기준으로 한다.

## 무료권 상태 전이

```text
available → reserved(comparison_id, generation, expiry)
reserved → consumed : 결과 저장 + 이용권 생성과 같은 트랜잭션
reserved → available : 작업 취소/최종 실패 확인 후 예약 해제
```

reservation 만료만 보고 다른 사람이 무료권을 쓰게 하지 않는다. 기존 job의 lease·fencing token을 무효화한 후 해제한다. 늦게 끝난 worker는 예약 generation 불일치로 결과/무료 소비 commit이 거절되어야 한다.

회원 전환 시 무료 이력을 유지한다. 이미 소비한 회원에게 guest의 새 무료권이 이관되도록 허용하지 않는다. 삭제·숨김·재설치로 동일 계정의 무료권을 복구하지 않는다.

## 유료 정상 흐름

1. 상대 입력 완료, 기존 접근 가능한 결과가 있는지 확인.
2. 구매 복원을 위해 영구 계정 연결. 입력과 comparison을 보존.
3. 서버에서 가격 2,900원과 comparison을 고정한 주문 생성.
4. PG 결제 UI 호출. 클라이언트는 발급된 주문과 금액을 전달.
5. 반환된 결제 정보를 서버가 저장된 주문과 대조하고 공급자 승인 API로 확인.
6. 공급자 상태·금액·통화·orderId 일치 확인.
7. DB 트랜잭션에서 주문 paid + entitlement active + generation job을 함께 commit.
8. 결과가 완성되면 결과 페이지와 지도에 반영.

클라이언트 success URL 도착만으로 paid 처리하지 않는다. 금액 1원으로 변경하거나 다른 사람의 주문 ID를 보내도 거절해야 한다.

## 주문과 결제 상태

orders: `created → confirming → paid → refund_pending → refunded`.

취소/실패/만료는 `cancelled / failed / expired`. 응답이 유실되면 `confirmation_unknown`으로 분류하고 공급자 상태 조회로 해결한다. 이때 새 결제를 바로 만들지 않는다.

payment_attempts는 각 승인 시도를 기록한다. 한 order에 여러 실패 시도가 있어도 성공 payment key는 중복 지급되지 않는다. 같은 payment key를 다른 주문에 연결할 수 없다.

## 장애와 복구

| 상황 | 동작 |
|---|---|
| 결제 창 취소 | 주문 상태 확인 후 입력 화면 복귀, 상대 정보 보존 |
| PG 승인 성공 후 DB 쓰기 실패 | 공급자 조회/웹훅/정기 대사로 paid·이용권·job 복구 |
| 승인 응답 유실 | uncertain 표시, 같은 주문 공급자 상태 조회, 재결제 유도 금지 |
| 동일 웹훅 여러 번 | 이벤트 키와 주문 상태로 멱등 처리 |
| 웹훅 순서 뒤바뀜 | 공급자 최신 상태 확인, paid가 오래된 pending 이벤트로 되돌아가지 않음 |
| 결제 완료 후 브라우저 종료 | 로그인 후 주문/결과에서 재개 |
| 결과 생성 반복 실패 | 같은 권한으로 재시도, 한도 초과 시 지원/환불 경로 |
| 환불 응답 유실 | 공급자 취소 상태 조회로 정합성 복구 |

외부 호출과 DB는 하나의 원자적 트랜잭션이 아니다. 서버 승인 경로, 검증한 웹훅, 주기적 reconciliation 세 경로가 동일한 멱등 처리 함수를 사용하게 한다.

## 환불

미제공/중복 승인 같은 기술 실패와 결과 열람 후의 요청을 구분한다. 구체적인 소비자 고지·환불 정책은 운영주체와 출시 전에 검토한다. 여기서는 법적 환불 가능 여부를 단정하지 않는다.

기술 흐름: 요청 기록 → 상태 확인 → provider refund/cancel 요청 → 확인 완료 → order refunded·entitlement revoked → 해당 공유 철회와 지도/열람 접근 정리. 결과 원본 및 회계 기록 보존은 데이터 정책을 따른다.

환불 요청 중에는 재생성을 멈추고, 늦게 온 worker가 취소된 권한을 다시 활성화하지 않도록 commit 시 권한 상태를 확인한다. 원문 카드 정보는 저장하지 않는다.

## 테스트 기준

- 첫 무료 요청 두 개 동시 실행 시 성공 한 건.
- 무료 결과 실패 시 안전한 예약 해제, 늦은 worker commit 차단.
- 유료 주문 더블 클릭 시 주문 한 개.
- 금액·소유자·주문 ID 변조 거절.
- PG 테스트 결제 → 결과 → 새로고침 → 재열람까지 성공.
- 승인 후 DB 중단 상황을 주입해 복구 성공.
- 웹훅 중복·역순·위조/미검증 이벤트가 이중 이용권을 만들지 않음.
- 환불/생성 경쟁에서 환불된 결과를 새로 공개하지 않음.

PG 후보는 Toss Payments다. 실제 계약·심사·결제수단·웹훅 검증 방법과 수수료는 연동 단계의 공식 문서 및 계약으로 확정한다.
