# 백업·알림 자동 실행 준비 · 2026-10-24

후속 [전체 출시 작업 실행](remaining-launch-execution.md)에서 관리 사본 순환·실제 DB 관측·실제 격리 복원에 연결한 백업 수집 옵션을 추가했다. 아래 ‘미연결’은 최초 file-cycle 범위의 기록이며, 현재 실행/보관/발송 활성화 여부는 후속 문서를 따른다.

현재 범위는 **로컬 파일 처리와 비발송 알림 대기열**이다. 외부 로그인·유료 전환·키 생성·원격 DB 내보내기·자동 스케줄 등록·보관 사본 삭제·메일/메신저 발송은 하지 않았다. 기존 [운영 기준](policies/release-decisions.md)과 [복구 절차](operations-recovery-preparation.md)의 미완료는 유지한다.

## 준비한 실행 도구

`web`에서 아래 명령을 실행한다. 경로는 설명용이며 실제로 만든 파일이 아니다. 저장소 밖 개인 소유 디렉터리700·파일600을 사용한다. 백업 원본·암호화 키·백업 저장 폴더를 각각 분리하며 원본과 키는 자동 삭제하지 않는다. 같은 디스크에 있는 여러 폴더는 독립 재해 백업이 아니다.

```sh
npm run backup:cycle -- --config /private/operations/backup-cycle.json
npm run alerts:queue -- --observation /private/operations/observation.json --directory /private/alert-state
```

첫 번째 설정 예시는 아래와 같다. 실행 전에 **실제 덤프 snapshot 시각**으로 갱신해야 한다. 파일 수정시각이나 명령 실행시각을 덤프 시각으로 대체하지 않는다. URL·DB 비밀번호·덤프 내용·암호화 키 원문은 JSON에 넣지 않는다.

```json
{
  "kind": "backup-cycle-file-v1",
  "input": "/private/dump-source/app.dump",
  "snapshotAt": "2026-10-24T01:00:00Z",
  "keyFile": "/private/backup-keys/app.key",
  "keyVersion": "staging-v1",
  "directory": "/private/backup-data"
}
```

`backup:cycle`은 이미 준비된 파일을 읽는다. DB 덤프 생성/DB 조회/업로드는 실행하지 않는다. 시각이 미래이거나1시간보다 오래됐거나 이전 기록 이하이면 실패한다. 입력이 실제 PostgreSQL 덤프라는 보증은 하지 않는다. 파일 암호화→인증 복호화→처리 전/후 원본과 복호화 파일의 SHA-256·크기 일치→복호화 임시본 제거→암호화 파일/비공개 catalog 기록 순서다. 실제 DB 복원은 별도이며 `restoreVerifiedAt:null`, 출력 `lastVerifiedBackupAt:null`을 유지한다. 이 출력으로 기존 알림의 ‘검증된 백업 최종 시각’을 올리지 않는다.

catalog는 원본/암호화 파일 해시·snapshot/완료 시각·키 버전·파일ID만 로컬에 보관한다. 키 원문·DB 주소·계정/생일/결과 본문은 저장하지 않는다. 7일 지난 항목은 파기 **후보 건수만** 출력한다. 실제 파기·기존 파일의 지속 무결성 검사·키 회전은 미연결이다.512개/256KiB 상한을 넘으면 기존 기록을 잃지 않고 중단하므로 자동 실행 전에7일 보관 순환기를 별도로 연결해야 한다.

알림 관측 형식은 `operations-observation-v1`로 [기존 설명](operations-recovery-preparation.md#7-외부-발송-없는-알림-판정)을 따른다. DB health 집계/성공 정리 시각/검증된 백업 근거를 수집하는 외부 어댑터는 미연결이다. 성공 근거가 없으면 null로 두며, 이전 관측을 현재 시각으로 재포장하지 않는다.

`alerts:queue`는 `alerts.json` 한 파일에 판정 이력과 후보를 함께 원자적으로 저장한다. 30분마다 같은 문제가 다시 판정되어도 동일 장애 시작 시각·문제/복구 이벤트별로 미발송 후보1개만 남긴다. 복구와 새 장애는 별개다. 후보는 코드·중요도·문제/복구·관측/장애 시작 시각만 담는다. `lastPlannedAt`은 송신 성공이 아니며 출력 `externalMessagesSent:0`, `senderConfigured:false`를 유지한다. 대기열128개 초과는 기록을 버리지 않고 실패한다. 송신·확인·삭제 명령은 제공하지 않는다. 향후 송신기는 오래된 문제/복구가 함께 대기한 경우 현재 상태와 대조하고, 성공/재시도/중복 방지 원장을 별도로 구현해야 한다.

두 도구는 상태 폴더의 배타 잠금으로 중복 실행을 거절한다. 중단 후 남은 잠금은 자동 탈취하지 않는다. 실행 프로세스·파일·이전 성공 상태를 확인하기 전 잠금을 지우지 않는다. 원자적 파일 교체와 파일 fsync를 사용하지만 전원 장애 시 디스크/파일시스템의 내구성까지 보장하지 않는다. JSON/파일 권한·심볼릭 링크·추가 필드·옵션 오류는 고정 오류코드만 반환하며 원문/경로/키를 출력하지 않는다.

## 아직 활성화하지 않은 주기

| 작업 | 채택 주기 | 자동 실행 전에 연결할 것 |
|---|---|---|
| DB 읽기 전용 관측→알림 대기열 | 5분 | 제한 역할·실제 관측시각·시각 역행 처리·집계 어댑터 |
| 일관된 DB snapshot→파일 백업 cycle | 매시간 | 원격 exporter·독립 저장소·키 관리자·월 복원과 구분한 성공 근거 |
| 7일 지난 암호화 사본 순환 | 매일 | catalog/실제 파일 대조·최신 유효 사본 보존·키 버전·삭제 기록 |
| 앱 초안/이벤트 정리 | 하루1회 | 기존 retention의 대상/권한 검토; maintenance/PG 재처리로 대체 금지 |
| 암호화 사본→격리 DB 복원 | 매월1회 |21테이블·ACL/RLS·버전·삭제/환불 최신 원장 재반영·복원 근거 보관 |
| 운영자 알림 전달 | 후보 발생 시 | 실제 수신처·이메일/보조 채널·발송 성공/재시도 원장 |

현재 Vercel 앱에 백업/관리 공개 API나 새 cron을 추가하지 않는다. Vercel 함수 임시 디스크를 장기 백업 저장소로 사용하지 않는다. 정기 실행을 활성화하려면 위 빈 항목을 확정하고 실패/재시작·복원·중복·보관량과 야간 알림을 실제로 시험해야 한다. 이번 재배포는 연구 스테이징 유지이며 운영/재해 복구·실청구 승인으로 부르지 않는다.

## 검증 범위

이전 커밋375bf99의 GitHub 검사3종은 최종 성공했다. 이번 도구는 합성 파일의 왕복/기록·오래된 원본/잘못된 권한/심볼릭 링크/잠금/용량 초과의 실패 보존·알림 재시작/중복/복구를 검사한다. `test:postgres`에서 실제 합성 pg_dump를 새 cycle로 암호화/기록한 뒤 별도로 복호화하여 격리 DB에 복원하고21테이블/스키마/ACL/RLS를 대조한다. 이 별도 훈련의 성공을 임의 운영 파일의 복원 성공으로 기록하지 않는다.
