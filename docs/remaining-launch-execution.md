# 남은 출시 작업 실행 · 2026-10-24

사용자의 ‘전부 진행’ 지시로 여섯 항목을 순서대로 확인했다. 백업 저장소와 운영 알림 수신처는 사용자가 ‘미정’이라고 답했다. 따라서 임의 저장소에 개인정보 사본을 올리거나 수신처를 만들지 않는다. 현재 연구 모드/실청구 차단을 유지하며 실제로 확인한 작업과 조건이 없어 실행하지 못한 작업을 아래에서 구분한다.

## 1. 백업 자동화

기존 `backup:cycle`에 더해 `backup:prune -- --directory /private/backup-data --plan` / `--apply`를 구현했다. 경로는 예시다. 관리 catalog와 암호화 파일 해시/권한을 먼저 대조하고, 최근7일 안의 사본이 하나 이상 남는 경우에만7일 경과 사본을 처리한다. 등록되지 않은 파일·키·원본 덤프는 삭제하지 않는다. 기본 자동 실행은 없다.

파기 전 catalog에 처리 예정ID를 원자적으로 기록한다. 도중 중단되면 새 백업 cycle이 중단하고, 같은 명령으로 이미 삭제된 파일을 건너뛰어 재개한다. 처리 기록을 지우고 최근 사본만 catalog에 남긴다. 삭제하지 않은 파일의 누락·해시 차이·심볼릭 링크·최근 사본 부재는 먼저 거절한다. 복원 가능성과 키 보존은 별도 확인해야 하며, 해시 일치만으로 월별 복원을 완료했다고 표시하지 않는다.

기존 `test:hosted-restore`에 선택적인 `--backup-directory /private/backup-data --key-file /private/backup-keys/app.key --key-version staging-v1` 옵션을 추가했다. 기존 필수7개 인자 뒤에 이 세 옵션을 정해진 순서로 붙인다. 오타/누락은 연결 전에 거절한다. 전용 설정/관리자 DB 연결을 읽기 전용으로 제한하고, 동일 DB snapshot 덤프→격리 로컬 복원/21테이블·ACL/RLS 대조를 실제로 통과한 뒤에만 암호화 cycle과 해당 바이트 해시에 대한 복원 확인시각을 기록한다. 파일 cycle 단독으로는 이 시각을 채우지 않는다. 원격 인증·스토리지·카카오/PG 상태는 검증 범위에서 제외한다.

실제 staging의 기본 비보관 모드로7초 동안 같은 복원 검사를 통과했고 원격 쓰기 없이 임시본을 제거했다. 저장소/키가 미정이므로 새 보관 옵션은 실제 데이터에 실행하지 않았다. 미완료: 독립 저장소/키 책임자·주기 등록·원격 장기 보관/파기와 장애 시 목표 시간 실측. 별도 최신 삭제/환불 원장은 아직 없다. 스케줄 설치를 켜기 전 이 항목을 연결한다.

## 2. 알림 자동화

`alerts:observe -- --settings .env.staging.local --project <전용 프로젝트ref> --directory /private/alert-state`를 추가했다. 설정 파일은 기존 사주 전용 서울/research/제한 역할/verify-full만 허용한다. 프로젝트ref는 비밀번호가 아니며, 다른 서비스 설정을 넣지 않는다.

DB 연결부터 default_transaction_read_only를 사용하고 일관된 읽기 전용 트랜잭션에서 현재 DB 시각·기존 health 집계·실제 마지막 retention 성공시각만 수집한다. DB 실패는 health:null 후보로 저장한다. 원문/개인·주문ID는 출력하지 않는다. 선택 옵션 `--backup-directory /private/backup-data`가 있으면 실제 복원 확인된 catalog 항목의 암호화 파일 해시/권한/시각을 다시 대조해 그 원래 snapshot 시각만 사용한다. 단순 암호화/최근 파일 시각을 백업 성공으로 승격하지 않는다. 확인 근거가 없거나 파일이 손상되면 null로 두어 계속 경고한다. 새 관리 API나 공개 모니터링 엔드포인트는 추가하지 않았다.

전용 staging 읽기 전용 실측에서 health ok, 미설정 백업/정리 근거 관련 활성 장애2개·후보2개, 실제 발송0건을 확인했다. 이 경우 DB health가 정상이어도 관측 명령은 종료2(needs attention)를 반환한다. 이 실행의 로컬 임시 대기열은 제거했다. 미완료: 수신처·송신기 성공/재시도 원장·외부 주기 실행.

## 3. 삭제·탈퇴와 과거 백업 복원

계정 개인자료 삭제에서도 작업 fence 증가와 함께 lease/error를 지우도록 맞췄다. 미확정 결제/환불은 여전히 먼저 해결한다. 주문/무료 이용 및 로그인 식별 표지 보존은 기존 정책과 같으며 이를 완전한 외부 인증 탈퇴로 부르지 않는다.

새 `recovery-overlay-v1`은 최신 계정 삭제/비교 삭제/주문 상태를 같은 읽기 전용 snapshot에서 식별자·상태·시각만 수집하는 라이브러리다. **독립적인 실시간 변경 원장이 아니다.** 운영 DB의 물리 파기 뒤 사라진 행을 권위 있게 증명하거나, 캡처 이후 변경을 커버하지 않는다. 실제 적용은 `saju_restore`라는 자체 격리 DB·Unix socket·saju_runtime 역할에서만 허용하고 원격/다른 대상은 거절한다. 일반 운영 apply CLI는 없다.

과거 백업→그 이후 이야기 삭제/계정 삭제/환불→과거 사본 복원→후속 상태 재반영을 실제 합성 PG로 검사했다. 모든 이전 공유/세션/초안/임시 인증·반환 정보는 닫고 작업을 취소/fence 처리한다. 삭제 대상은 비우고 환불 권한은 회수하며, 소유권이 바뀐 항목·오래된/미래/관계가 맞지 않는 후속 상태는 거절한다. 최신 사본에만 있는 신규 구매는 재구성하지 않고 누락 수를 보고한다. `serviceResumeApproved:false`, `independentJournalVerified:false`를 유지한다. 운영 복구에는 쓰기 정지 이후 독립 원장/PG 대사·새 로그인·재개 검증이 더 필요하다.

외부 탈퇴 검수: 현재 콜백은 Supabase/Kakao provider 토큰을 장기 보관하지 않는다. [Supabase 공식 사용자 삭제](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser)는 서버 관리자 권한이 필요하고 [카카오 공식 연결 끊기](https://developers.kakao.com/docs/ko/kakaologin/rest-api#unlink)는 사용자 액세스 토큰 또는 해당 앱 어드민 키/검증된 회원번호 방식이다. 현재 로컬 설정에서 해당 두 관리자 자격은 미설정임을 값 출력 없이 확인했다. 새 관리자 키를 앱에 추가하거나 실제 계정을 지우지 않았다. 사용자 요청/서버 소유권→미확정 거래 해결→독립 요청 원장→앱 접근 차단/삭제→공급자 단계별 처리·영속 성공/실패/응답 유실 재시도→최소 tombstone·재가입/무료권 정책 검증을 갖춘 뒤 활성화한다. Supabase 삭제만으로 카카오 연결 해제가 됐다고 표시하지 않는다.

## 4. NICEPAY 거래 웹훅

현재 키의 읽기 전용 조회는 canonical card registered다. 실제 staging DB의 NICEPAY 거래 이벤트0개·전액 취소 테스트 주문3개를 확인했다. NICEPAY 관리자 화면은 로그인으로 돌아와 발송/재전송 로그를 열 수 없었다. 기존 취소 거래를 재승인하거나 합성 서명을 거래 수신 증거로 사용하지 않았다. 관리자 로그인 후 기존 승인/취소 발송 로그와 재전송부터 대조할 단계가 남았다.

## 5. 풀이·정책 출시 후보

출시 후보의 구현 범위는 기존 계산v5/신규 풀이v9·점수 없는 전체 알려진 기둥 설명·친구/연인/가족/동료별 본문으로 유지한다. 시간 모름/역사 시계/절입 후보 보호와 과거 구매 스냅샷을 바꾸지 않는다. 일반 강약/중화·합화 최종 판정·궁합 점수는 미검증이므로 새로 활성화하지 않는다. 기존 원고968사례 검사와 소스 명세를 재검사하며, 실제 전문가 서명을 만들어내지 않는다.

판매자 상호는 기존 지정 플로렌스랩이다. 대표자·사업자/신고·주소·문의 이메일·개인정보 책임자는 미정이며 임의로 채우지 않는다. 보관/7일 자율 환불 등 채택값은 기존 초안대로 유지한다. 실제 법률 검토/위탁·국외 이전/타인 정보 처리 근거/법정 거래 분리 보관·종료 파기와 게시가 남았다. 현재 앱 자료 삭제를 법정 기록 자동 분리 완료로 표시하지 않는다.

`npm run launch:check`는 [운영자 설정 예시](launch-operator-settings.example.json)의 빈 항목을 고정 코드로 출력한다. 실제 값은 저장소 밖600 JSON을 만들고 `--config`로 확인한다. 신고 대상 제외 등은 실제 사업자 판단/근거로 기록하고 임의 면제 문자열을 넣지 않는다. 이 명령은 자체 신고 필드 점검이며, 값/체크를 채워도 observedEvidenceVerified/publicReleaseApproved/realChargesEnabled는 false다. 키·결제 승인·정식 게시를 실행하지 않는다.

## 6. 실결제·최종 공개

현재 NICEPAY sandbox 보호를 유지한다. 운영 계약/키·서버 승인/취소·실거래 웹훅·영수증/문의·개인정보/환불 운영·지속 백업/감시·외부 탈퇴·감수 결과와 실제 기기/인앱 검증을 구체적으로 확인한 뒤 전환해야 한다. 이번 ‘전부 진행’은 미확인 계약/사업자 정보/전문 검증의 완료 증거가 되지 않는다. 사용자 이해도 관찰은 이전 지시대로 생략하고 새 관찰 결과를 만들지 않는다.


정책 원문 대조: 2026-10-24 국가법령정보센터에서 [개인정보 보호법 제21조](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900078981)의 파기/법령상 보존분 분리와 [전자상거래법 시행령 제6조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1018638379)의 표시·광고6개월/계약·철회 및 결제·공급5년/불만·분쟁3년을 재확인했다. 기존 초안의 기간과 일치한다. 이 원문 확인으로 실제 데이터의 분리/파기 구현이나 최종 사업자 법률 검토가 완료되지는 않는다.
