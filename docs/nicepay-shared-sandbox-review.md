# 기존 NICEPAY 테스트 상점 연결 검수

2026-10-22. 사용자가 NICEPAY 로그인을 완료한 뒤 관리자 UI를 직접 확인했다. 실제 과금용 `플로렌스랩(Florence Lab)`과 별도로 **다니엘의 노트 테스트** 상점이 있다. 테스트 상점 개발정보에 **S2 Server 승인 클라이언트 키 / Basic 인증 시크릿 키**가 이미 있다. 새 상점을 만들거나 키를 재발급하지 않았다. 운영 R2 키를 사주 앱에 복사하지 않았다.

## 연결 전 확인과 보류

기존 테스트 키를 Git 제외 로컬 설정(권한600)과 Vercel `chunbae-staging`의 서버 환경에 저장하는 단계, 테스트 웹훅 `https://chunbae-staging.vercel.app/api/nicepay/webhook` 추가는 사용자 확인을 요청한 상태다. 새 서버에 이 테스트 상점 거래 조회·승인·취소 권한이 생기며, 같은 테스트 상점의 전자책 알림도 전달될 수 있기 때문이다. 실제 키 값은 채팅·검사 출력·Git에 남기지 않는다. 현재 확인만으로 키 저장/실제 결제 완료로 바꾸지 않는다.

공식 [샌드박스 안내](https://github.com/nicepayments/nicepay-manual/blob/main/common/test.md)는 계정당 테스트 상점 하나와 과금 없는 테스트를 설명한다. 샌드박스 응답은 실제 거래와 다른 임의 값일 수 있으므로 실운영 승인 증거로 재사용하지 않는다. 기존 전자책 운영 상점·키·결제·코드는 수정하지 않는다.

## 공유 상점 웹훅 문제와 보완

기존 수신기는 주문번호를 바로 UUID로 제한했다. 전자책의 다른 형식 주문번호나 사주 DB에 없는 주문은400/503으로 처리될 수 있었다. 같은 상점을 공유하면 불필요한 재전송이 생길 수 있으므로 다음처럼 보완했다.

- JSON/필드 형식·서명을 먼저 검증한다. 위조·잘못된 입력은400으로 거절하고, 원문 오류/요청·구매자 필드는 로그/DB에 저장하지 않는다.
- 서명이 유효한 다른 형식 또는 사주 DB에 없는 주문은 `OK`로 응답한다. 결제사 조회·승인·취소와 사주 결제 이력 저장을 하지 않는다.
- 우리 주문은 금액·이미 연결된 TID가 일치해야 한다. 알림의 `status`를 신뢰해 권한을 주지 않고 기존 결제사 조회로 현재 상태를 확인한다.
- JSON 순서·추가 구매자 정보와 무관하게 서명 필드로 이벤트 식별자를 만든다. 중복 이벤트도 현재 결제 상태는 다시 대조하므로 뒤늦은 취소를 놓치지 않는다.
- 결제사 조회 장애는503을 유지해 재시도할 수 있게 한다. 성공 이벤트나 결과 권한을 만들지 않는다.

공식 [웹훅 명세](https://github.com/nicepayments/nicepay-manual/blob/main/api/hook.md)는 JSON 통보, 서명/금액 검증과 `text/html`의 `OK` 응답을 요구한다. [거래 조회](https://github.com/nicepayments/nicepay-manual/blob/main/api/status-transaction.md)의 현재 상태·주문·금액·서명 대조를 유지한다. R키 차단이나 승인 전 거래 소속 확인을 완화하지 않았다.

## 검증 범위

합성 검사에는 다른 서비스의 일반/UUID 주문 무시, 위조 거절, 중복 알림의 이벤트1개, 잘못된 상태 알림보다 결제사 현재 상태 우선, 금액/TID 불일치 거절, 취소 뒤 결과 권한 제거, 조회 장애의503/권한 미생성을 포함한다. 실제 상점 API 요청·카드 결제창·승인/조회/취소와 원격 웹훅 왕복은 별도 검증이 필요하다.

웹161개·HTTP/모바일28개·Next/Vercel 빌드와 소스 현황/문서 검사를 통과했다. 소스7df465e를 기존 서울 스테이징에 [재배포](server-staging-deployment.md)하고 랜딩200·개인 API401·잘못된 JSON 웹훅400/no-store·기존 프로필 새로고침 유지를 확인했다. 키 연결은 승인 대기이며, 이 응답 검사를 결제사 알림 왕복으로 간주하지 않는다.
