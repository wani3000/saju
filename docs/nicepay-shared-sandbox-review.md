# 기존 NICEPAY 테스트 상점 연결 검수

2026-10-22. 사용자가 NICEPAY 로그인을 완료한 뒤 관리자 UI를 직접 확인했다. 실제 과금용 `플로렌스랩(Florence Lab)`과 별도로 **다니엘의 노트 테스트** 상점이 있다. 테스트 상점 개발정보에 **S2 Server 승인 클라이언트 키 / Basic 인증 시크릿 키**가 이미 있다. 새 상점을 만들거나 키를 재발급하지 않았다. 운영 R2 키를 사주 앱에 복사하지 않았다.

## 연결 승인과 설정

사용자가 테스트 키 저장·서버 연결·웹훅 추가를 승인했다. 기존 S2/Basic 키를 Git 제외 로컬 설정(권한600)과 전용 Vercel 서버의 sensitive 환경에 저장했다. 설정11개이며 staging 사전 검사 누락0개다. 운영 R키·기존 전자책 설정·관리자 DB 자격은 변경하거나 배포하지 않았다. 실제 키 값은 채팅·검사 출력·Git에 남기지 않는다.

공식 [샌드박스 안내](https://github.com/nicepayments/nicepay-manual/blob/main/common/test.md)는 계정당 테스트 상점 하나와 과금 없는 테스트를 설명한다. 샌드박스 응답은 실제 거래와 다른 임의 값일 수 있으므로 실운영 승인 증거로 재사용하지 않는다. 기존 전자책 운영 상점·키·결제·코드는 수정하지 않는다.

## 공유 상점 웹훅 문제와 보완

기존 수신기는 주문번호를 바로 UUID로 제한했다. 전자책의 다른 형식 주문번호나 사주 DB에 없는 주문은400/503으로 처리될 수 있었다. 같은 상점을 공유하면 불필요한 재전송이 생길 수 있으므로 다음처럼 보완했다.

- JSON/필드 형식을 검증한다. 우리 주문이 될 수 없는 비UUID 번호는 거래 처리 없이200/OK로 버린다. 이는 서명 인증 성공이 아니며 DB·결제사 조회·이력 저장을 하지 않는다. 등록 확인의 샘플 알림도 이 범위다. UUID 주문은 서명을 먼저 검증하며 위조·잘못된 입력은400으로 거절한다. 원문 요청·구매자 필드는 로그/DB에 저장하지 않는다.
- 형식이 유효한 비UUID 번호 또는 서명이 유효하지만 사주 DB에 없는 UUID 주문은 `OK`로 응답한다. 결제사 조회·승인·취소와 사주 결제 이력 저장을 하지 않는다.
- 우리 주문은 금액·이미 연결된 TID가 일치해야 한다. 알림의 `status`를 신뢰해 권한을 주지 않고 기존 결제사 조회로 현재 상태를 확인한다.
- JSON 순서·추가 구매자 정보와 무관하게 서명 필드로 이벤트 식별자를 만든다. 중복 이벤트도 현재 결제 상태는 다시 대조하므로 뒤늦은 취소를 놓치지 않는다.
- 결제사 조회 장애는503을 유지해 재시도할 수 있게 한다. 성공 이벤트나 결과 권한을 만들지 않는다.

공식 [웹훅 명세](https://github.com/nicepayments/nicepay-manual/blob/main/api/hook.md)는 JSON 통보, 서명/금액 검증과 `text/html`의 `OK` 응답을 요구한다. [거래 조회](https://github.com/nicepayments/nicepay-manual/blob/main/api/status-transaction.md)의 현재 상태·주문·금액·서명 대조를 유지한다. R키 차단과 승인 응답의 주문/금액/TID·서명 검증을 유지한다. 카드 인증 뒤 최초 승인은 아래의 검증된 return 경로로만 실행한다.

## 검증 범위

합성 검사에는 다른 서비스의 일반/UUID 주문 무시, 위조 거절, 중복 알림의 이벤트1개, 잘못된 상태 알림보다 결제사 현재 상태 우선, 금액/TID 불일치 거절, 취소 뒤 결과 권한 제거, 조회 장애의503/권한 미생성을 포함한다. 실제 상점 API 요청·카드 결제창·승인/조회/취소와 원격 웹훅 왕복은 별도 검증이 필요하다.

웹161개·HTTP/모바일28개·Next/Vercel 빌드와 소스 현황/문서 검사를 통과했다. 소스7df465e를 기존 서울 스테이징에 [재배포](server-staging-deployment.md)하고 랜딩200·개인 API401·잘못된 JSON 웹훅400/no-store·기존 프로필 새로고침 유지를 확인했다. 키 연결은 승인 대기이며, 이 응답 검사를 결제사 알림 왕복으로 간주하지 않는다.


## 실제 현대카드 인증에서 발견한 승인 순서 오류

합성 전용 계정/주문2,900원을 만들고 실제 S2 결제창에서 사용자가 현대카드 앱 인증을 완료했다. 서버 return의 nonce·서명 검증은 통과했지만 승인 전 GET 거래 조회가404/U107이어서 앱은 `confirmation_unknown`을 보존했다. [공식 Server 승인 명세](https://github.com/nicepayments/nicepay-manual/blob/main/api/payment-window-server.md)는 인증 성공 뒤 POST 승인을 수행하고, [거래 조회](https://github.com/nicepayments/nicepay-manual/blob/main/api/status-transaction.md)는 승인 결과 확인에 사용한다고 설명한다. 이 카드 인증 상태를 조회 가능한 `ready` 거래로 가정한 합성 transport가 실제 차이를 놓쳤다.

해당 인증된 합성 주문/TID만 별도로 S2 승인했다. 실제 응답의 주문·TID·금액·통화·서명이 모두 일치했다. 이후 기존 서비스로 재조회/paid 복구→유료 결과 생성/열람→전액 테스트 취소→결제사 CANCELED/DB refunded→결과 접근 거절→합성 개인정보 제거까지 확인했다. 실제 청구·기존 카카오 사용자/무료권 변경은 없었다. 이 첫 검사를 앱 자동 return 왕복 성공으로 기록하지 않는다.

수정은 nonce·주문·clientId·금액·인증서명이 모두 검증된 return에만 주문/TID 범위의 첫 승인 capability를 부여한다. 일반 confirm/대사/웹훅 경로는 임의 TID를 처음 승인하지 않는다. 최초 승인 응답도 전체 서명과 주문/금액/통화/TID가 맞아야 권한을 준다. U107은 GET404의 정확한 경우에만 미조회로 구분하며, 재전송은 먼저 조회해 이미 승인된 주문을 다시 POST하지 않는다. 다른 주문 응답·응답 유실·위조 return·일반 U107의 승인 금지를 회귀 검증했다.

## 웹훅 등록 확인 요청

관리자 등록 확인은 비UUID 주문번호18자·TID30자·금액 숫자·일시28자·서명64자리의 샘플 JSON을 보냈지만 저장한 상점 서명과 일치하지 않았다. 요청의 값·개인정보 없이 타입/길이만 임시 진단했고 진단 코드는 제거했다. 우리 UUID 주문의 서명을 생략하지 않고, 우리 주문번호 공간 밖의 유효 형식 알림을 거래 처리 없이 폐기하도록 정리했다. 알 수 없는 UUID는 여전히 유효 서명이 있어야 DB 조회하며, 실제 주문은 결제사 현재 상태로만 권한을 바꾼다.

수정 후 canonical URL의 신용카드 웹훅 등록을 완료했다. NICEPAY 관리자의 TEST호출도 성공했다. 이 샘플은 폐기 응답 검증이며 우리 거래의 서명 대사 검증과 구분한다. 새 합성 주문의 수정된 자동 return 왕복은 현대카드 앱 재인증 대기다. 실제 운영 결제/정식 출시 승인은 별도다.

웹165개·타입·Next/Vercel 빌드·일반 HTTP/모바일28개와 별도 NICEPAY HTTP 검사를 통과했다. 별도 HTTP는 완전히 격리한 임시 로컬 DB/공개 합성 키만 사용하며 등록 샘플의200/no-store, 위조 UUID400, JSON/과다 요청400/413, GET405, 서명 유효 미소유 주문200, 잘못된 return400을 확인한다. 외부 상점이나 실제 사용자 정보가 들어가지 않는다.


## 2026-10-23 재인증 재개

사용자가 새 앱 인증 완료를 알렸지만 브라우저의 결제 완료 단계에서 현대카드가 `hz0001`(입력 시간 초과)을 표시했다. 해당 합성 주문은 DB created·payment_key 없음, 서버 결과 미도착이며 return nonce도 만료돼 있었다. 만료를 연장하거나 성공으로 처리하지 않았다. 이전 창/검증 서버를 닫고 소유 합성 계정에 카카오 identity가 없음을 확인한 뒤 개인정보를 제거했다. 미승인 주문은 cancelled로 정리했다.

같은 실제 청구 불가 S2·현대카드·일시불2,900원 조건으로 새 합성 주문/nonce와 인증 창을 준비했다. 앱 인증 직후 브라우저의 결제 완료까지 사용자가 눌러야 자동 검증에 도착한다. 현재 이 재인증을 기다린다. 앞선 실제 승인/전액 취소 성공과 수정 후 자동 return 미완료는 구분한다. 코드 변경은 없으며 GitHub19b4a12의 Research/Web/Prototype CI 세 가지 성공을 확인했다.
