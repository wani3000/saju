# 사주 계산과 궁합 해석 설계

## 세 층을 구분한다

1. 달력과 날짜 계산: 양력/음력/윤달, 시간대, 절입 시각을 처리한다.
2. 명리 규칙: 선택한 관습에 따라 사주와 관계 요소를 산출한다.
3. 서비스 표현: 내부 비교 지표와 쉬운 풀이, 지도 거리를 만든다.

달력의 검증 가능한 사실과 해석상의 선택을 혼동하지 않는다. 궁합 점수는 과학적으로 검증된 실제 관계 확률이 아니다. ‘87% 확률로 잘 맞는다’ 같은 표현을 쓰지 않는다.

## 2026-10-09 검증 업데이트

[1차 실제 결과](engine-validation.md)에 따라 ssaju 현재 커밋은 제외하고 manseryeok을 다음 검증 대상으로 선정했다. 아래 초기 후보 목록은 검토 이력이다. 운영 채택은 아직 보류한다.

## P01 엔진 후보와 평가

- 우선 후보: `golbin/ssaju`. 공개 문서에는 음양력 변환과 사주 계산, MIT 라이선스가 안내되어 있다.
- 비교 후보: `yhj1024/manseryeok`. 채택 전 코드·LICENSE·버전과 지원 범위를 별도 확인한다.
- 달력 대조: 한국천문연구원 음양력 자료. 정확한 절입 시각 검증에는 별도의 신뢰할 수 있는 시각 자료를 확보한다. 절기 날짜만으로 분 단위 경계를 검증할 수 없다.
- API 대안: SAZU. 자체 엔진 검증 실패 또는 일정 변경 시 공급 조건을 확인하고 선택한다.

두 후보가 서로 같다는 것만으로 정확하다고 판정하지 않는다. 데이터 원천이 같을 수 있기 때문이다. README의 지원 범위와 정확도 주장은 코드·독립 사례로 확인한다.

## 계산 정책 초안

| 항목 | 기준/결정 절차 |
|---|---|
| 초기 지역 | 국내 출생 우선. 해외는 별도 지원 전 차단 |
| 지원 연도 | 1900년~현재를 목표로 검토하되, 통과한 범위만 공개 |
| 양력/음력 | 입력 구분과 윤달을 보존하고 정규 양력 날짜를 함께 저장 |
| 연주·월주 | 채택한 절입 기준을 명시하고 정확한 시각 경계 검증 |
| 일주 날짜 변경 | 23시/0시 관습 중 하나를 P01에서 감수와 함께 확정 |
| 출생 시간 모름 | null, 시주 및 시간에 의존하는 요소 제외 |
| 과거 표준시·서머타임 | 고정 UTC+9로 처리하지 말고 해당 지원 연도별 정책 검증 |
| 태양시 보정 | 경도 보정과 진태양시를 혼동하지 않음. MVP 적용 여부를 명시적으로 결정 |
| 성별/대운 | MVP는 대운을 사용하지 않음. 라이브러리의 기본 성별에 따라 불필요한 결과가 달라지지 않게 함 |

시간을 알고 입력한 경우에도 지도 지표는 모든 사람에게 공통으로 있는 연·월·일 기준을 우선 제안한다. 시간 정보는 상세 풀이 보완에만 사용하면 ‘시간 모름’ 사람의 거리와 비교가 일관된다. 최종 감수에서 이 기준을 확정하고 사용자에게 계산 범위를 설명한다.

## 엔진 계약

입력: calendar_type, year, month, day, is_leap_month, birth_time 또는 null, time_known, 출생 지역/시간대 정책.

출력: 정규화한 날짜, 연·월·일주, 선택적 시주, 필요한 오행/상호작용, 입력 제한, applied_policies, engine_version, 원천 자료 버전.

시간이 없는데 후보 엔진이 기본 12시를 넣는다면 어댑터가 관련 시주·종속 값을 제거하거나 엔진을 수정한다. 시간 미상 테스트가 통과하지 않으면 채택하지 않는다.

## 궁합 규칙 구조

관계 비교 함수는 두 사람의 계산 결과를 받고 근거가 있는 features를 만든다. 예시는 오행 구성의 보완과 선택한 합·충 등의 상호작용이다. 어떤 요소를 쓰고 얼마의 비중을 둘지는 현재 미확정이다.

규칙 레코드에는 `rule_key`, `version`, `condition`, `effect`, `explanation_key`, `rationale`, `review_status`를 둔다. 조건은 제한된 표현식 또는 코드로 정의하며 DB의 임의 문자열을 실행하지 않는다.

- 모델/LLM에게 0~100점을 임의로 생성하게 하지 않는다.
- 감수 전 임시 가중치는 개발 fixture로만 사용한다.
- 규칙 충돌 시 우선순위와 상한/하한, 동일 점수 처리 기준을 정한다.
- 자기 궁합, 순서 교환 A/B, 음력과 대응 양력 등 불변성 테스트를 둔다.
- 가족·연인·친구에 따라 조언 문구는 달라도 지도 거리 산식은 하나로 유지한다.
- 점수 근거 feature와 적용 규칙 ID를 저장해 설명과 숫자가 모순되지 않는지 검증한다.

## 풀이 DB 제작

원본은 `content/`의 리뷰 가능한 파일로 관리하고 승인된 release만 DB에 배포한다. 관리 화면은 MVP에서 만들지 않는다.

각 문구: `template_key`, 적용 조건, 관계 유형, title, body, 금지/주의 표현 검사, 검토자, status, content_version.

출력은 `summary`, `strengths[]`, `differences[]`, `advice[]`, `details[]`로 고정한다. 각 항목 길이와 개수 제한을 둔다. 반드시 기본 fallback 문구가 있어야 하며 문구가 없으면 타인의 관계 설명을 대신 사용하지 않는다.

검토 순서: 규칙 정의 → 명리 감수 → 쉬운 한국어 편집 → 실제 결과 조합 검토 → 승인 release. 문장이 자연스러워도 판단 근거가 불분명하면 운영에 넣지 않는다.

## 엔진 통과 기준

- 출처가 명시된 200개 이상의 달력 대조 사례를 목표로 수집한다.
- 별도로 절입 전후 1분, 날짜 변경 전후, 윤달, 시간 모름, 표준시 변화를 포함한다.
- 검증한 정책 아래 치명적인 날짜/주 계산 불일치가 남아 있으면 출시하지 않는다.
- 과거 정책을 지원하지 못하면 지원 연도를 줄이고 화면에서 안내한다.
- 기대값, 출처, 시간대, 적용 관습을 fixture마다 기록한다.
- 구매한 결과는 버전 고정. 새 release 도입 전 기존 fixture 전체를 재검증한다.

위 수치와 기준은 계획이며 테스트 통과 사실이 아니다.
