## 설계에서 구체화한 선택

- `web/`를 실제 서버 연결 코드로 만들고 기존 `prototype/` 보호 런타임은 유지했다.
- PostgreSQL 버전별 migration과 체크섬 이력을 작성했다. 소유자·비교·주문 FK, 금액과 상태 CHECK, 무료권 owner 유일성, job/result/entitlement 비교 유일성을 DB에서 제한한다. 예정된 20개 테이블을 모두 만들었다는 뜻이 아니다. 현재 출생/차트는 비교 JSONB 불변 스냅샷으로 보관하고, 별도 프로필 버전 테이블은 정식 계정 도입 시 확장한다.
- PGlite는 Node 프로세스 안에서 PostgreSQL을 실행하는 개발 저장소다. 다중 프로세스 운영/분산 동시성 검증의 대체재가 아니다. 모든 소유 데이터는 서버 경유로만 접근한다.
- 무료권·결제/환불 상태·이용권·job은 분리했다. worker commit은 소유자 잠금, lease/fence, 무료 reservation generation 또는 유료 active entitlement를 재검사한다.
- 비교 중복 검사는 사람 UUID와 정규 양력 날짜·시간을 기준으로 하며 이름/관계 표시는 과금에 영향을 주지 않는다. JSONB의 키 정렬이 달라도 같은 비교로 인식한다. 기존 결과는 원래 이름/관계/문구를 보존한다.
- 시간 모름·과거 시간대 연구 정책은 기존 어댑터를 재사용한다. 번들 생성 시 고정 Seoul fixture를 포함하며 원본은 변경하지 않았다. engine policy의 productionApproved=false를 유지한다.
- 아직 승인된 궁합 규칙이 없으므로 점수는 null, 문구는 example-copy-v1 고정 예시다. 실제 사주 기둥과 예시 풀이를 UI에서 분리했다.
- 개발 복구 코드는 256비트 난수이며 hash만 저장한다. 복구 시 같은 owner와 무료 이력을 유지하고, 계정 전환은 자동 병합하지 않는다. PKCE 연결·이관 코드는 추가했으며 실제 OAuth 왕복은 아직 검증하지 않았다.
- 공유 토큰은 hash만 저장하고 허용된 별명/풀이/캐릭터만 snapshot으로 생성한다. 링크가 로컬 서버를 가리키므로 일반 지인에게 보내는 공개 서비스는 아직 아니다.
- Toss는 테스트 키만 허용한다. 공급자 호출을 기다리는 동안 DB transaction을 유지하지 않는다. 승인/취소 응답이 미확정이면 성공을 표시하지 않고 조회/재시도 경로를 둔다.
- 웹훅은 힌트로만 사용한다. DB 주문에 연결된 공급자 조회가 일치해야 권한을 바꾸며 중복·역순 이벤트도 현재 상태를 기준으로 처리한다. 실제 웹훅 수신은 외부 테스트 단계에서 검증해야 한다.

## 다음 실제 서비스 연결 순서

1. Supabase 테스트 프로젝트·카카오 공급자 설정 → PKCE 실제 왕복 → 전용 외부 DB role·계정 이관 재검증. 로컬 PostgreSQL 동시성/복원 검증은 완료.
2. 독립 절입 자료와 감수자를 통해 연구 계산 정책·궁합 규칙·문구를 승인. 승인 전 실제 궁합 점수나 유료 풀이로 전환하지 않음.
3. NICEPAY 테스트 키로 승인/취소/응답 유실/웹훅을 실제 왕복 검증. 현재 통과한 것은 모의 공급자와 내부 테스트다.
4. 도메인·호스팅·운영 정책 확정, 로그 마스킹·worker·대사·백업복원·삭제 절차를 staging에서 검증한 후 출시 판단.

외부 프로젝트를 생성하거나 비용/실결제를 발생시키지 않았고, 공개 배포도 하지 않았다. 지금 바로 확인 가능한 결과는 로컬 개발 앱이다.
