# 품질 검증과 운영 준비

2026-10-14 구현 상태: [서버 연결 앱](../web/README.md)과 [완료/미완료 대조](server-app-status.md)를 먼저 확인한다. 아래 상세 설계에는 운영 전 예정 항목도 포함된다.

## 검증 층

| 영역 | 필수 검증 | 완료 기준 |
|---|---|---|
| 달력·사주 | 독립 기대값, 윤달, 절입 전후, 시간 모름, 과거 시간 정책 | 지원 범위 안 치명적 불일치 없음 |
| 궁합·풀이 | 결정성, 규칙 근거, 금지 표현, 문구 누락 | 같은 버전 같은 출력, 승인 콘텐츠만 운영 |
| DB·권한 | 타 계정 조회/수정, FK owner 일치, 익명 계정 이관 | 교차 소유 데이터 접근 실패 |
| 무료권 | 동시 요청, 만료 예약, 늦은 worker | 무료 결과 한 건, 실패 시 복구 |
| 결제 | 금액 변조, 중복, 응답 유실, 대사, 환불 | 금전과 권한 상태 일치 |
| 공유 | 토큰 추측, 철회, 만료, 원문 누출 | 허용 필드만 공개 |
| 지도 | 거리 순서, 고정 위치, 1/2/8/20명, 목록 | 읽고 선택 가능, 기존 결과 불변 |
| 접근성 | 큰 글씨, 명암비, 200% 확대, 키보드, 보조기기 | 핵심 흐름의 접근 불가 결함 없음 |
| 전체 여정 | 첫 무료 → 공유 → 유료 추가 → 지도 → 재열람 | 각 단계 실패/복구 포함 통과 |

## 핵심 인수 사례

- AT01: 신규 방문자가 내 정보와 상대 정보를 입력해 무료 전체 결과를 받는다.
- AT02: 같은 결과를 새로고침해도 무료권이 다시 소비되거나 결과가 달라지지 않는다.
- AT03: 두 번째 상대는 2,900원 안내 후 테스트 결제를 거쳐 결과가 나온다.
- AT04: 첫 상대와 두 번째 상대가 같은 지도에 보인다. 각 노드에서 맞는 결과가 열린다.
- AT05: 기존 사람을 누르면 재결제 없이 결과를 읽는다.
- AT06: 이름 수정은 무료이며 생년월일 변경과 구분된다.
- AT07: 나의 출생 정보 수정 시 기존 구매 결과가 조용히 바뀌지 않는다.
- AT08: 미상 출생 시간이 실제 null이며 시주를 만들지 않는다.
- AT09: 결제 후 브라우저를 닫아도 계정에서 결과를 복원한다.
- AT10: 공유 미리보기에 다른 사람의 지도/생일이 없고 철회 후 접근할 수 없다.
- AT11: 계정 A가 계정 B의 person/result/order ID를 넣으면 접근이 거절된다.
- AT12: 중복 웹훅과 승인 응답 유실에도 결과 구매 권한은 하나만 생긴다.
- AT13: 무료 생성 job이 중단된 뒤 재개되어도 무료권/결과가 중복되지 않는다.
- AT14: 가입한 계정과 guest 내 정보 충돌을 자동 덮어쓰지 않는다.
- AT15: 환불된 결과는 이용권·공유·지도 정책과 일치한다.

## 테스트 자료

실제 사용자와 지인의 생일을 테스트 파일에 넣지 않는다. 명시적으로 만든 합성 날짜를 사용한다. 계산 fixture는 provenance와 기대값을 가진다. 테스트 시각/타임존을 고정하고 무작위 케이스는 seed를 남긴다. 스크린샷에는 가상 별명을 사용한다.

## 성능 목표 초안

모바일에서 입력 반응을 지연시키지 않고, 이미 저장한 결과 재열람은 빠르게 보여준다. 초기 예산은 저장 결과 API p95 1초 이내, 자체 계산 포함 신규 결과 p95 5초 이내로 제안한다. 실제 호스팅/네트워크 환경에서 측정해 조정하며 현재 측정값이 아니다. 처리 중에는 무한 로딩 대신 상태·재시도·문의 경로를 준다.

## 관측

요청 ID, 익명화/최소화한 내부 식별자, 처리 단계, 시간, 오류 코드만 수집한다. 생일·풀이 전문·결제키·공유 토큰·인증 토큰을 로그와 분석 도구에 넣지 않는다. 유료 승인 건수와 active entitlement 수, 큐 체류 시간, 재시도/환불 pending 시간을 점검한다.

결제 이상과 결과 생성 정체 알림의 대상·기준·연락 채널은 운영자가 정한다. 이 준비 작업에서 실제 알림이나 예약 작업을 생성하지 않는다.

## 데이터 보호

전송 암호화, 관리형 저장 암호화 조건을 확인한다. 운영자 최소 권한, 개인 데이터 삭제·공유 철회, 원문을 제외한 분석 이벤트를 기본으로 한다. 생년월일 HMAC도 개인정보 처리를 대체하는 익명화가 아니다. 제3자 출생 정보 처리, 이용 연령, 동의 문구, 보존 기간, 환불 고지는 출시 전 정책 검토가 필요하다.

## 배포와 복구

1. dev/staging/prod 환경과 키 분리.
2. staging migration/seed/전체 E2E 통과.
3. 운영 migration 전 백업과 복원 방법 확인.
4. schema 확장은 먼저, 구버전 앱과 호환 유지, 데이터 채우기, 나중에 제거.
5. 배포 후 합성/테스트 가능한 범위의 확인 및 PG 상태 점검.
6. 앱 오류는 이전 앱 버전으로 복귀. DB 파괴적 변경을 자동 역실행하지 않음.
7. 결제·작업 처리 중단 후 provider 상태 대사로 권한을 복구.

백업 주기·보존·RPO/RTO는 선택한 서비스 플랜 확인 후 확정한다. 최소 출시 조건은 백업에서 별도 환경으로 복원하는 리허설 1회다. 백업 존재만으로 복구 가능하다고 기록하지 않는다.

## 출시 차단 조건

달력 경계 오류, 미감수 궁합 규칙, 타 계정 데이터 접근, 결제/이용권 불일치, 공유 원문 노출, 핵심 버튼 접근 불가, PG 운영 계약/필수 고지 미완료가 있으면 출시하지 않는다. 사소한 장식 개선과 출시 차단 결함을 구분한다.

## 2026-10-20 출시 준비 실행 자료

현재 실행 순서·정책 확정 항목·접근 제한·지연 큐/결제/복원·배포 복귀는 [운영 실행 절차](launch-operations-runbook.md), 실제 전문가·사용자 검토는 [감수 실행 묶음](launch-review-kit.md)을 따른다. 템플릿·로컬 점검이 완료됐다는 사실을 실제 승인·외부 운영 완료로 해석하지 않는다.
