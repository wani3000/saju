# 운영·복구 준비 · 2026-10-23

현재 범위는 기존 research staging의 운영 준비다. 로그인·원격 maintenance/worker·새 스케줄러/알림·유료 플랜·운영 키·실청구·원격 복원/역마이그레이션을 실행하지 않는다. [현재 출시 상태](launch-status-current.md)와 [정책 확정 목록](policies/release-decisions.md)의 미확정은 유지한다.

## 1. 모니터링 실행안

현행 `npm run health`는 집계만 읽는다. `npm run maintenance`는 거래 조회/취소 재처리·작업·만료 정리를 실행하므로 상태 조회 명령으로 대신 사용하지 않는다. 잘못된 옵션은 연결 전에 종료1이다. 연결할 스케줄러·담당자·알림 수신처·실행 역할은 미정이며, 이 문서의 주기는 제안이다.

| 신호 | 확인/대응 | 제안 |
|---|---|---|
| health 종료1 | DB/설정/접속 문제. 고정 오류코드만 기록 | 5분마다 읽기 전용 점검, 연속 실패 시 담당자 알림 |
| FAILED_JOBS / EXPIRED_LEASES | 실패/임대 만료 원인과 기존 작업 상태 확인 | 개인정보 없이 사유/건수만 전달, 확인 후 worker 재개 |
| DELAYED_QUEUE | 비교 생성 후300초 넘은 queued. 순수 큐 대기 시간 아님 | worker 중단/재시도 확인. 같은 결과를 새 주문으로 만들지 않음 |
| PENDING_PAYMENTS | 승인/취소 미확정 | PG 기존 거래 조회·대사 우선. 중복 결제나 이미 취소한 거래 재승인 금지 |
| 백업/정리 마지막 성공 누락 | 작업 실패·보관량/접근 설정 확인 | 마지막 성공·기간·상태 집계. 생일/주문ID/세션/공유 토큰 제외 |

실제 운영 실행과 자동 복구 권한을 분리한다. 장애 알림을 채팅/이메일로 보내는 연결은 수신처와 권한이 정해진 뒤 구성한다. 로그가 없다는 한 번의 조회를 지속 감시 성공으로 표시하지 않는다.

## 2. 백업 범위와 승인할 선택

[Supabase 공식 백업 문서](https://supabase.com/docs/guides/platform/backups)는 유료 플랜의 일일 백업과 무료 플랜의 외부 내보내기 권고를 구분한다. 무료 프로젝트에 내려받을 수 있는 관리형 백업/PITR이 있다고 가정하지 않는다. DB 백업은 Storage 객체를 대신하지 않고 사용자 지정 DB 역할의 비밀번호도 별도 준비가 필요하다.

기존 [실제 staging 앱 DB→격리 로컬 복원](hosted-backup-restore-check.md)은 public21테이블만 검증했다. Supabase auth/스토리지·제공자 설정·DB 비밀번호·카카오/PG 상태까지 복구한 증거가 아니다.

운영자 선택 후보: 일일 암호화 외부 백업·최근7일 보관·월1회 격리 복원. 저장소/키 관리자·접근자·비용·보관 종료/파기 책임자를 확정하기 전 자동 업로드하지 않는다. RPO(허용 데이터 손실 구간)와 RTO(복구 목표 시간)는 미정이다. 일일 백업이면 백업 사이의 신규 구매·삭제·철회가 빠질 수 있으므로 유료 운영의 목표와 PG/삭제 이력 대사 방식도 별도로 결정한다.

## 3. 복구 순서

1. 장애 범위와 마지막 정상 커밋/배포ID, 백업 생성 시점·무결성·버전·접근 승인 기록을 확보한다. 쓰기/결제/작업 처리를 멈추거나 통제할 방식과 재개 책임자를 정한다. 운영 DB에 덮어쓰며 시험하지 않는다.
2. 격리 DB·격리 역할로 복원한다. 실제 PG 키/worker/사용자 쿠키를 복원본에서 사용하지 않는다. 테이블·스키마·ACL/RLS·마이그레이션 체크섬과 소유권을 대조한다.
3. 아래 호환성 검사로 대상 앱/worker가 저장 결과와 미처리 작업의 버전을 지원하는지 확인한다. 통과해도 외부 상태의 최신성을 증명하지 않는다.
4. 백업 이후의 환불/삭제/공유 철회·신규 주문을 별도 권위 있는 기록과 대사한다. 삭제된 개인정보나 철회 링크가 되살아나지 않게 재반영하고, 세션을 재사용하지 않으며 인증 연결 재검증 계획을 확인한다. 현재 별도 최신 이력 저장소/재반영 자동화는 미구축이다. 증거를 확보하지 못하면 서비스 재개를 보류한다.
5. 합성 계정으로 새 로그인·기존 스냅샷 열람·무료/유료 권한·환불 접근 회수·공유 철회·작업의1회 재개를 확인한다. 실제 재로그인/PG 대사는 외부 인증 가능할 때 진행한다.
6. 누락 범위·실측 복구 시간·담당자·재개 승인·임시본 제거를 기록한다. 이전 앱으로 복귀하더라도 DB 역마이그레이션이나 과거 결과 재생성을 자동 실행하지 않는다.

## 4. 앱/worker 버전 호환성 검사

[현재 소스 명세](audits/runtime-recovery-manifest.json)는 지원 엔진/풀이와 마이그레이션 해시만 담는다. **반드시 복귀할 그 배포를 만든 커밋에서 생성한 명세**를 사용한다. 현재 명세를 과거 앱의 지원 범위로 사용하면 안 된다. 과거 명세가 없으면 해당 커밋의 지원 범위를 검토해 확보하기 전 복귀하지 않는다.

```sh
cd web
npm run recovery:manifest -- --check
npm run recovery:check -- --target /private/target-runtime.json --inventory /private/restored-inventory.json
```

두 번째 명령의 경로는 준비한 비공개 JSON으로 바꾼다. 원본 덤프·행·연결 문자열·비밀키를 넣지 않는다. 각 파일64KiB 상한이며 추가 필드/옵션은 거절한다. 네트워크/DB에 접속하거나 복원·배포·작업을 실행하지 않는다. 종료0은 구조 호환,2는 버전/마이그레이션 불일치,1은 입력 오류다. 결과의 `productionRecoveryApproved`는 항상 false다.

복원 DB의 읽기 전용 동일 snapshot에서 아래 집계를 얻는다. migration 항목은 `schema_migrations`의 name→name/checksum→sha256으로 변환한다. 각 버전 목록은 중복을 제거한다. 사용자ID나 결과 본문은 필요 없다.

```json
{
  "kind": "recovery-inventory-v1",
  "schemaMigrations": [{"name": "001_core.sql", "sha256": "실제 원장 체크섬64자리"}],
  "storedEngineVersions": ["실제 comparisons.engine_version 값"],
  "storedReadingVersions": ["실제 comparisons.rule_version 값"],
  "pendingReadingVersions": ["awaiting_payment/queued/processing/failed 비교의 rule_version 값"]
}
```

위 형태 설명의 문자열은 실제 유효 입력이 아니다. 원장의 모든 마이그레이션을 넣고 누락/빈 DB 여부를 확인한다. 단순히 현재 명세를 복사해 복원 DB 조사 결과로 쓰지 않는다. `test:postgres`는 격리 복원 DB에서 이 집계를 실제로 수집해, 현재 앱 호환·v9를 모르는 이전 worker의 대기 작업 거절을 검사한다.

## 5. 이번 실행과 남은 운영 준비

로컬 합성 PostgreSQL에서 백업→다른 DB 복원→21테이블/권한/스냅샷/작업 재개 및 버전 호환성을 검증하고 실행 결과를 기록한다. 이 훈련은 장기 백업 저장이나 전체 Supabase 재해 복구를 대신하지 않는다.

미확정: 운영 예산/플랜·저장소/암호화 키 관리자·RPO/RTO·정기 작업/알림·보관/삭제 처리·최신 취소/삭제 이력의 별도 보존·외부 인증/PG 복구·재개 책임자. 정식 공개/실청구 승인을 자동으로 붙이지 않는다.
